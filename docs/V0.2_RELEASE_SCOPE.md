# v0.2.0 release scope

This document separates ordinary-mode runtime work, required verification, live
acceptance, and release operations. Passing unit tests is not a substitute for the
listed live checks.

## 1. Ordinary runtime baseline

v0.2.0 has one user task path: an ordinary Codex Thread selected in the Houdini
Panel. The central composer, attachments, Native Goal, Focus, Stop/Continue,
diagnostics, and HIA MCP V2/HOM execution are all bound to that Thread.

The baseline includes:

- pinned Codex app-server integration with zero runtime approvals;
- live Web Search behavior for ordinary Threads;
- Launcher-generated, project-local Qwen environment propagation through Bridge to
  HIA MCP and the knowledge CLI;
- explicit Local Knowledge import and refresh, resumable vector construction,
  signature-aware status, and strict lexical versus hybrid/vector behavior;
- ordinary text, image, image-only, and Steer requests;
- ordinary history create, resume, rename, copy ID, delete, refresh, and selection;
- explicit `hia_project_memory` operations, which remain a user-controlled durable
  memory tool and are unrelated to the removed project-team runtime;
- one ordinary SceneWriter boundary with real Thread, Turn, HIA item, and terminal
  release identities;
- ordinary Native Goal and Focus, with Stop pausing automatic continuation;
- third-real-compaction rotation for ordinary Threads only; and
- a single viewport capture implementation using `SceneViewer.flipbook`, writing
  only below `.runtime/cache/screenshots`.

Native model subagents may still provide bounded read-only assistance when the model
supports them. The plugin does not create, name, schedule, persist, or grant Houdini
write access to fixed role Threads.

## 2. Removed experimental scope

The experimental fixed five-role project-team mode was removed before v0.2.0 because it destabilized ordinary operation and had not completed embedded Houdini acceptance.

There is no hidden mode, feature flag, compatibility shim, project HTTP surface,
project registry reader, project data migration, or project data cleanup. Existing
legacy files under `.runtime` remain untouched and are ignored by the new runtime.
Git history and the dedicated archive branch preserve the abandoned implementation.

## 3. Required verification

Before the release candidate, verification must cover the ordinary Bridge Session and
HTTP paths, ordinary Panel history and composer wiring, ordinary attachments, Native
Goal and Focus, ordinary third-compaction rotation, HIA MCP V2, diagnostics, release
hygiene, and one clean current-Python full test run. GitHub Actions is authoritative
for the Python 3.10, 3.11, and 3.13 matrix.

Source and release-package checks must confirm that no project-team routes, role
runtime modules, project Panel modules, project schemas, or project attachment paths
remain. They must also confirm that `.runtime`, `.venv`, local credentials, tests,
HIP files, renders, and machine-local files are excluded from the public archive.

## 4. Live Houdini acceptance

The current Launcher and Bridge must be started normally against the supported
Houdini installation. Acceptance requires an embedded Panel ordinary Thread to create
and resume tasks, send text and image inputs, Steer and Stop a live Turn, use Native
Goal and Focus, execute and validate a bounded HIA MCP V2/HOM edit, refresh ordinary
history, and complete one viewport capture below
`<project-root>/.runtime/cache/screenshots`.

Standalone Qt and `hython` offscreen tests are not Embedded Houdini Pane acceptance.
Record the exact Houdini build and direct evidence for every live check that actually
runs, and mark anything else unverified.

## 5. Release operation

The ordinary cleanup branch is not merged directly. Its verified changes are
squash-merged into a release branch based on the latest `main`, reviewed as one clean
ordinary-runtime diff, and opened as a new Draft pull request. No tag or GitHub Release
is created until that Draft PR, its CI matrix, and the required embedded Houdini
acceptance are complete and the user gives separate release authorization.
