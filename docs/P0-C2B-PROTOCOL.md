# P0-C2B stable app-server protocol baseline

## Scope and evidence

This baseline is an offline analysis of the non-experimental JSON Schema generated by the pinned, verified Codex CLI 0.144.3. The source Schema is committed at `schemas/codex-app-server/0.144.3` in commit `84f25b4823d7704f51c576efee89e084f1bcc93f`. All four aggregate schemas declare JSON Schema draft-07.

P0-C2B did not start `codex app-server`, log in, run a Turn, connect to Houdini, start a network service, or invoke an executable from the local Codex toolchain. It did not use `--experimental`.

The machine-readable baseline consists of:

- `contracts/codex-app-server/0.144.3/protocol-inventory.json`: all 87 client requests, 10 server requests, 68 server notifications, one client notification, and 97 response-schema documents, with aggregate and response SHA-256 values.
- `contracts/codex-app-server/0.144.3/core-allowlist.json`: the deny-by-default stable core, explicit exclusions, transport boundary, and compatibility decisions.
- `src/hia_core/codex_protocol.py`: a read-only, standard-library validator for the frozen inventory and allowlist.
- `tests/unit/test_codex_protocol_contract.py`: offline contract tests; no package installation or service startup is required.

## Stable core allowlist

The Bridge may depend only on the methods in this section. Every other generated method is denied until a later versioned contract explicitly admits it.

### Client requests

| Method | Response Schema |
|---|---|
| `initialize` | `v1/InitializeResponse.json` |
| `thread/start` | `v2/ThreadStartResponse.json` |
| `thread/resume` | `v2/ThreadResumeResponse.json` |
| `thread/read` | `v2/ThreadReadResponse.json` |
| `thread/fork` | `v2/ThreadForkResponse.json` |
| `turn/start` | `v2/TurnStartResponse.json` |
| `turn/interrupt` | `v2/TurnInterruptResponse.json` |

The required client notification after initialization is `initialized`.

### Approval requests from the server

| Method | Client response Schema |
|---|---|
| `item/commandExecution/requestApproval` | `CommandExecutionRequestApprovalResponse.json` |
| `item/fileChange/requestApproval` | `FileChangeRequestApprovalResponse.json` |
| `item/permissions/requestApproval` | `PermissionsRequestApprovalResponse.json` |

The legacy `applyPatchApproval` and `execCommandApproval` request names are not in the stable core. The Bridge must not silently translate between legacy and stable approval methods.

### Streaming and lifecycle notifications

The allowed stream includes:

- General state: `error`, `warning`, `deprecationNotice`, `guardianWarning`, and `configWarning`.
- Thread state: `thread/started`, `thread/status/changed`, `thread/tokenUsage/updated`, and `thread/compacted`.
- Turn state: `turn/started`, `turn/completed`, `turn/diff/updated`, and `turn/plan/updated`.
- Item state: `item/started`, `item/completed`, and `item/agentMessage/delta`.
- Reasoning stream: `item/reasoning/summaryTextDelta`, `item/reasoning/summaryPartAdded`, and `item/reasoning/textDelta`.
- Approved command/file activity: `item/commandExecution/outputDelta`, `item/commandExecution/terminalInteraction`, `item/fileChange/outputDelta`, and `item/fileChange/patchUpdated`.
- Tool and request flow: `item/mcpToolCall/progress` and `serverRequest/resolved`.
- Model lifecycle: `model/rerouted`, `model/verification`, and `model/safetyBuffering/updated`.

These notifications allow the Panel to render text, plans, reasoning summaries, approvals, tool progress, diffs, completion state, warnings, and token usage without storing a second chat history.

## Explicit exclusions

The protocol is deny-by-default and additionally freezes the following named exclusions:

- Experimental Schema and methods: no `--experimental`; no `experimentalFeature/list`, `experimentalFeature/enablement/set`, `item/tool/requestUserInput`, or schema-declared experimental `item/plan/delta` dependency.
- `dynamicTools`: no `item/tool/call` dependency. Houdini tools are supplied by the project-scoped MCP host instead of dynamic app-server tools.
- Process API: no `command/exec`, `command/exec/write`, `command/exec/terminate`, `command/exec/resize`, `command/exec/outputDelta`, `process/outputDelta`, or `process/exited` dependency.
- Thread shell execution: no `thread/shellCommand` dependency.
- WebSocket transport: no `ws`, `wss`, or app-server WebSocket dependency. Bridge-to-app-server transport is stable stdio JSONL only.

Realtime thread notifications, filesystem APIs, account APIs, plugin/marketplace APIs, Windows sandbox setup, remote control, fuzzy search, and all other generated surfaces remain outside the core because they are absent from the allowlist.

Unknown server requests are rejected. Unknown notifications are logged and ignored with a metric so an additive notification cannot crash the Panel, but it gains no behavior until admitted by a reviewed contract.

## Offline contract guarantees

The standard-library validator and tests enforce:

1. Codex version, contract format, and JSON Schema draft remain pinned.
2. Aggregate SHA-256 values, method discriminators, parameter-definition references, titles, and declared experimental markers exactly match the inventory.
3. Every local JSON Schema `$ref` resolves inside its document; external Schema references are rejected.
4. All 97 response Schema paths and SHA-256 values match the generated tree, with no missing or duplicate response document.
5. Every allowlisted method exists in the proper request/notification direction and retains its parameter definition.
6. Every allowlisted response Schema exists.
7. Experimental, dynamic-tool, process, shell-command, and WebSocket surfaces remain excluded.
8. Only stdio JSONL is accepted as the Bridge-to-app-server transport.

These are structural, hash-pinned offline contract tests. They do not claim a live app-server handshake or runtime behavior; that remains a separately authorized P1 integration test.

## Codex 0.144.3 upgrade compatibility strategy

A Codex upgrade must never replace this baseline in place.

1. Verify and install the candidate CLI in a new project-local version directory under the existing safety policy.
2. Generate non-experimental Schema into a new `schemas/codex-app-server/<version>` directory.
3. Generate a new inventory and compare request, response, notification, definition, and hash changes against 0.144.3.
4. Block the upgrade if an allowlisted method disappears, changes direction, becomes experimental, changes its parameter definition, loses its response Schema, or gains a new required field or narrower accepted type without an adapter and explicit review.
5. Treat added optional fields and added non-allowlisted methods as potentially compatible only after the offline contract suite passes. They do not automatically enter the core allowlist.
6. Reject any upgrade that makes the core depend on WebSocket, `dynamicTools`, process APIs, or `thread/shellCommand`.
7. Add a new versioned contract directory and keep the 0.144.3 files intact. If two versions must coexist, select an explicit version adapter; never auto-negotiate an unreviewed surface.
8. Keep 0.144.3 as the rollback baseline until the candidate passes offline contracts and a separately approved live integration matrix.

P1 remains blocked until this offline baseline passes and the user separately authorizes P1. P0-C2B itself provides no runtime connection capability.
