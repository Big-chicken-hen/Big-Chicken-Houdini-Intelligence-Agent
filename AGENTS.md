# Repository agent rules

These rules have the highest priority for every development round in this repository.

## Safety boundary

1. The only project root is `E:\houdini-intelligence-agent`.
2. Never create project files, virtual environments, caches, renders, HDAs, logs, checkpoints, jobs, quarantine data, or temporary files on `C:`.
3. Never modify `C:\Users`, AppData, a user home directory, `CODEX_HOME`, Houdini user configuration, or any drive root.
4. Before any future delete or move, perform a read-only inventory, canonicalize every exact target, prove it is strictly inside the project root, reject UNC/device/ADS/path-escape/reparse-point targets, show the exact scope, and obtain separate explicit user approval.
5. Never recursively delete a computed, expanded, uncertain, or unverified path. Do not provide a general recursive-delete product tool.
6. On Windows, keep filesystem operations in one native PowerShell/Windows call chain, use literal paths and argument arrays, and never pass PowerShell-enumerated paths to another shell.
7. Do not use `git reset --hard`, `git checkout --`, force-overwrite, or silently discard user work.
8. Read existing files before modifying them. Preserve unrelated user changes.
9. Do not install dependencies or create a virtual environment unless the user explicitly authorizes the implementation stage. Keep any later approved runtime data under the project `.runtime` directory.
10. Bind every future local control service to `127.0.0.1` and authenticate it. Never expose the Houdini gateway or Codex app-server directly to a LAN or the internet.
11. Never fabricate test results, Houdini connections, node operations, screenshots, renders, schema discovery, or HIP/HDA understanding.
12. Run all tests that can run, report actual results, and label tests that cannot run as unverified with the reason.

## Product boundary

- Codex is the only intelligent agent. Do not build a second Agent, LLM, planner, RAG system, vector database, semantic-memory service, or external vision model.
- Houdini supplies UI, deterministic tools, scene execution, and artifacts. Do not control Houdini through screen takeover or Computer Use.
- Codex-native subagents may be introduced only in the authorized phase. The live HIP remains single-writer, and subagents return proposals by default.
- SQLite may eventually store technical state and audit metadata, but not a duplicate chat history, embeddings, semantic summaries, or a custom memory system.
- Knowledge retrieval and preference storage do not train or alter model weights; describe them accurately.

## Development boundary

- Follow the active phase only. Never begin a later phase implicitly.
- Keep protocol bridge, MCP transport, Houdini gateway, context adapters, tools, jobs, validation, approvals, audit, and UI in separate modules.
- Return structured, JSON-serializable user-facing errors; tracebacks may be diagnostic logs but never the only user-facing response.
- Never expose arbitrary shell execution, `exec`, or `eval` as an unrestricted product tool.
- Never modify a Houdini scene without the approval required for that exact operation and risk level.
- Discover the active Houdini installation and live schema at runtime; do not hard-code a Houdini version or install path. The live schema is authoritative when it conflicts with static material.
- Do not permanently limit the Houdini graph engine to the first certified catalog. Admit later node types or Houdini contexts only through separately reviewed catalog/protocol versions and context-specific risk policy; do not add per-node handlers or a general DCC abstraction.
- Never automatically save or overwrite HIP files, modify HDA definitions, delete nodes, or scan arbitrary filesystem locations.

Gate B4A authorizes only one dormant, dependency-injected Houdini HOM graph write adapter and its minimal fake-HOM tests. The adapter may receive a `hou_module`, read adapter, UI-main-thread identity, and clock through explicit construction, but it must not import `hou`, PySide6, or Qt; start a thread, process, service, or background task; provide `main()`; or expose an environment, configuration, command-line, default-constructor, or network enable path. No production entry point may import, construct, register, or call it.

Production remains strictly read-only. The stdio MCP, Bridge, Panel dispatch, launcher, app-server command, and project `.codex/config.toml` continue to expose exactly `houdini_scene_info` and `houdini_node_type_info`; `houdini_graph_validate`, `houdini_graph_apply`, and `houdini_graph_verify` remain unregistered and uncallable. The tracked project server remains `enabled = true` and `required = false`; only the Bridge-owned app-server child may override it to `required=true` through a per-process `-c` argument. B2C attestation, status, lease, redaction, and executor-credential controls remain unchanged.

The adapter is not an approval authority. It may consume only an already normalized graph paired with the exact internal `SceneQueue` request and executor claim. An injected claim authority must first seal that exact, non-cancelled request/claim object pair into an opaque execution token, then redeem that token exactly once when `apply_prevalidated` starts; a copied, reconstructed, cancelled, absent, previously sealed, or replayed claim/binding grants no authority. The adapter must then recompute the graph and approval-binding digests. Caller fields such as `approved=true`, `allow=true`, or `confirmed=true` grant no authority. Before the first HOM mutation it must fail closed unless the injected UI-main-thread identity, write latch, deadline/cancel/shutdown state, HIP session, scene revision, `/obj` fingerprint, exact target absence, live catalog, safe parameter definitions, transaction/request identity, and non-blocking single-writer guard all match the binding.

The first B4A certified catalog contains `Object/geo`, `Sop/box`, `Sop/transform`, `Sop/merge`, and `Sop/null`, with live `Sop/transform` resolving to `xform`. It is the first reviewed catalog, not a permanent writer boundary. One catalog-driven Houdini graph engine must translate both table and stairs without asset-specific branches. Future types or contexts require new reviewed catalog/protocol versions and risk policy, not per-node handlers or a general DCC framework. B4A adds no type, context, Schema, protocol version, dependency, queue, registry, database, service, or feature-flag system.

The adapter may create only one new validated `/obj/HIA_Graph_<id>` Object/geo root and its declared owned children. Every child creation uses the common catalog-resolved `createNode` path with `run_init_scripts=False`. Before the returned root or child receives any later mutation, the adapter must prove it is one exact new identity and matches the approved name, exact path, resolved type, session identity, parent identity, parent membership, and exact `hou_module.node(path)` registry lookup. An absent, pre-existing, substituted, aliased, or ambiguously registered return is indeterminate and freezes writes. It may use only typed parameter setters for the frozen safe parameters, connect only object references created by the current transaction, and set only declared flags. It must never search for, modify, reconnect, rename, move, or delete pre-existing content; use expressions, HScript, Python SOPs, arbitrary user-data keys, `exec`, `eval`, `compile`, shell, or subprocess; or save, cook on demand, render, cache, publish an HDA, or write an external file.

All mutations must occur inside exactly one injected `hou_module.undos.group("HIA: Apply Graph")` and follow the seven existing stages: `create_root`, `create_nodes`, `set_parameters`, `connect_nodes`, `set_flags_layout`, `postcondition`, and `commit`. One mandatory atomic control guard must wrap every HOM mutator, non-cancellable rollback/Undo/revision containment, and the final commit boundary; a control outcome cannot be followed by another mutation. The guard is not trusted to preserve thread affinity: every `mutate`, `contain`, and `finalize` callback must re-assert Houdini UI-main-thread identity at callback entry before touching adapter, scene, Undo, observer, or revision state. Undo-group factory, `__enter__`, and `__exit__` failures are contained explicitly. A factory failure before enter is recoverable only when no boundary was attempted; any `__enter__` or `__exit__` exception is indeterminate, freezes later writes, and permits no blind follow-up mutation. A root or child `createNode` call that may have partially mutated before raising but returned no exact identity is likewise indeterminate and freezes later writes. A missing candidate output follows the same confined rollback, one Undo-close attempt, outcome publication, and proof path as every other pre-commit failure; it may not return through an ad hoc shortcut.

The injected clock is untrusted input. Every value used at adapter entry and again inside locked preflight must be a finite, non-negative number; an exception, boolean, non-number, NaN, infinity, or negative value fails closed before Undo entry with zero fake-HOM mutation and zero revision change. These checks are fake-HOM safety evidence only and do not verify real Houdini thread scheduling or timing behavior.

Publication of every `committed`, `rolled_back`, or `indeterminate` outcome must invoke its guarded callback exactly once and return that exact report object. After an `indeterminate` publication that retains an owned scope, one bounded best-effort refresh must install observers on that retained root and its direct children before a separately sampled capability report is accepted, even when finishing the owned write failed. If the commit path already attempted its refresh, containment must not retry it. The published/refreshed and independent reports must agree on availability, session, outcome-specific revision and fingerprint, and catalog; an indeterminate reported revision must be at least `base_scene_revision + 1`. Disagreement cannot report success or a proven rollback.

The mandatory postcondition may read only the retained owned root and its direct declared children; it must not recursively scan `/obj`, substitute request state for observation, echo layout as observed, or fabricate a layout mutation. Success and rollback both require `hou_module.node("/obj")` to remain the exact retained parent and every pre-existing `/obj` child identity/fingerprint to remain unchanged. The root's direct children must equal the complete declared retained-child set by identity, session, exact path, name, and resolved type. An extra, replacement, missing, or partially created but unreturned child makes ownership unprovable and forbids blind rollback.

Success requires every approved path lookup to resolve to the exact retained object, the root to have zero input and output connections, and the children's full input and output connection collections to have exactly the declared cardinality with both endpoints resolving by identity inside the current transaction. After successful Undo exit, the adapter must repeat the complete observed-state verification before publishing success. Before rollback may destroy the root, the same bidirectional connection confinement must hold. Any external-to-owned or owned-to-external edge makes blind destruction forbidden and the state indeterminate. After destruction, the root path and every retained-child path must be absent and the exact parent/pre-existing fingerprint restored; after Undo exit, those rollback proofs must be repeated before publishing a proven rollback. Unprovable or failed rollback returns the frozen indeterminate result and latches later writes. `KeyboardInterrupt` and `SystemExit`, including one raised during rollback, complete best-effort containment or freeze before the applicable interruption is re-raised.

Read-adapter callback coalescing makes only this B4A claim: if fake-HOM actually delivers an event while an exact expectation is armed, the callback source must be the registered object identity; for rollback `ChildDeleted`, that source is the retained parent, not the deleted root. A delivered mismatched, external, late, or off-main-thread event invalidates the owned write. Zero delivered events are neither proof of no mutation nor proof that a real HOM call is observable, and B4A must not claim every live mutator emits a callback. Observer installation on newly created nodes and reliable event coverage for `createNode`, `setUserData`, parameter, connection, flag, and destruction calls are unresolved B4B capability-probe blockers. The fake successful-commit observer refresh and report agreement do not remove that blocker.

Fake-HOM must model only the HOM calls the adapter actually makes, preserve a pre-existing sentinel, and fault-inject every mutation stage. A successful fake apply enters exactly one fake Undo group and advances the existing scene revision exactly once. This evidence proves only call order, state transitions, and safety guards; it does not prove real Houdini Undo, cook, callback, rollback, or version compatibility.

Gate B4A does not authorize importing or calling real `hou`, starting Houdini or hython, modifying a real HIP, running a real MCP/Bridge/app-server chain, enabling a graph tool, or entering Gate B4B. Future Gate B4B requires separate approval and is limited to one selected fixture, one apply in one blank unsaved disposable HIP, and one manual Undo. Do not modify frozen Schema, fixtures, production wiring, configuration, launchers, services, contracts, or project-external files during B4A. Dynamic Bridge and executor credentials must not appear in B4A source, configuration, results, diagnostics, or tests. Keep every B4A change unstaged and uncommitted until the user separately reviews and approves a commit.
