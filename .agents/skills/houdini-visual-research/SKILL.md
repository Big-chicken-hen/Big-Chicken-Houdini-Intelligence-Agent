# Houdini Visual Research

Apply professional visual judgment without making small requests heavyweight. Keep Codex as the only intelligent decision-maker.

## Route the request

1. Decide whether uncertainty warrants the shared lookup in [knowledge-and-memory.md](references/knowledge-and-memory.md). A known deterministic parameter, connection, delete, rename, position, or color edit executes directly and ends with targeted validation; it needs no local or web research. When node/parameter behavior, version support, a complex material/simulation/Solaris workflow, historical project convention, or failure cause is uncertain, run one relevant batched local lookup before the affected write. If the main task or another active Houdini Skill already completed it, reuse that compact result instead of searching again. For complex, multi-domain, unfamiliar, or version-sensitive work, retrieve only the relevant bundled SideFX workflow and version evidence before planning.
2. Select the Direct, Focused, or Full route in [build-brief-and-review.md](references/build-brief-and-review.md). Direct work executes immediately and ends with one necessary targeted validation; it does not require retrieval, external research, a Brief, capture, or artifact review. Focused work adds only the one or two evidence steps that address its actual uncertainty.
3. Use the Full route for simulation/cache work, substantive material or color-managed rendering, reference matching, unfamiliar or version-sensitive behavior, high-cost operations, and multi-stage deliverables. This is risk reasoning, not a gate or fixed state machine; a simple color assignment remains Direct.
4. When complete or substantial reference-driven construction is requested, define the observable target and completion evidence; use `$houdini-procedural-modeling` to own model structure, procedural construction, and editability. An explicitly requested blockout, proxy, placeholder, or technical test may still use this skill for reference research, but does not trigger `$houdini-procedural-modeling` or get promoted to full construction.
5. Treat reference matching, unfamiliar modeling or FX methods, substantive material and look development, rendering, simulation, animation, lighting, or final-image work with a meaningful visual result as complex research or visual judgment. Complete any uncertainty-triggered local lookup and necessary external web research before writing; choose semantic depth (`light` or `deep`) from [research-and-sources.md](references/research-and-sources.md), without fixed call counts.
6. Use deep research when the user cites ShaderToy, GLSL, a paper, or an unfamiliar technique, or when Houdini/version behavior is uncertain. Continue automatically across as many research rounds and sources as the evidence needs; prefer original sources and current SideFX material.
7. Treat an ordinary HOM/tool syntax or runtime error as execution diagnosis, not visual research by itself. Preserve the exact error and fix it directly; use [visual-validation.md](references/visual-validation.md) for failed complex visual work or explicit dissatisfaction, and research only when the failure exposes an unfamiliar or version-sensitive technical question.

Manually searching this repository's src, services, or contracts is software development, not visual research. A relevant `hia_local_help_search` match from published Skills or approved current project documentation is local knowledge retrieval; it does not authorize reading ordinary project source. Read that source only when the user explicitly asks to develop or debug the plugin.

## Load only the needed guidance

- Read [knowledge-and-memory.md](references/knowledge-and-memory.md) when node/parameter/version behavior, complex workflow, historical project context, or failure cause is uncertain. Skip it for a known deterministic edit.
- Read [build-brief-and-review.md](references/build-brief-and-review.md) to choose the risk tier. Load its full Brief/review guidance only for a Full task, substantial rebuild, consequential staged handoff, professional review, or Verified Procedure decision.
- Read [technique-selection.md](references/technique-selection.md) for complex tasks, reference-driven assets, or uncertainty between SOP/VEX, COP, MaterialX, DOP/solvers, Solaris/LOPs, and Karma.
- Read [research-and-sources.md](references/research-and-sources.md) whenever external sources or reference works are involved.
- Read [shader-translation.md](references/shader-translation.md) for ShaderToy, GLSL, screen-space effects, ray marching, or shader-inspired work.
- Read [visual-validation.md](references/visual-validation.md) for every complex task before judging completion and for any failure or explicit dissatisfaction report.

Keep references one level deep; do not load unrelated references.

## Execute proportionally

1. For a Direct edit, obtain only required scene context, execute, and run one targeted validation over the affected path or value. Stop without retrieval, a Brief, capture, or review when that evidence settles the request.
2. When retrieval informs Focused or Full work, turn relevant field rules, mappings, ranges, and version limits into explicit semantic expectations before writing. After execution, ask the current `hia_validate` semantic-expectation capability to test those claims using its live tool contract. A clean cook is not proof that, for example, `flame` mapped to `flame`, required fields are active, or velocity is finite and scale-plausible.
3. For the Full route, create the compact Build Brief from [build-brief-and-review.md](references/build-brief-and-review.md) using any retrieval evidence, external research, and necessary scene context. Keep its goal, design language, subsystems, editable controls, outputs, risks, applicable stages, and acceptance evidence current; separate user constraints from assumptions.
4. When a Full task needs subjective effect judgment for simulation, procedural modeling, materials, lighting, rendering, or animation, use the temporary, bounded comparison contract in [visual-validation.md](references/visual-validation.md). Keep its EffectSpec and Codex evaluation only in the current task context. Direct deterministic work never enters this loop.
5. For substantial modeling, provide reference decomposition, technique choices, and visual iteration guidance to `$houdini-procedural-modeling`; let it own model structure, controls, and network editability. For other visual work, build a parameterized, inspectable network in coherent stages.
6. Prefer this authoring order: edit suitable existing nodes and parameters; add standard native Houdini nodes and networks; use a short cohesive HOM batch to orchestrate the smallest complete change; create geometry directly or use an in-scene Python/script node only when the earlier options cannot reasonably express the result. Record the reason for an exception and validate its inputs, output, and time or dependency behavior. Treat each `hia_execute_hom` batch as a bounded change. After failure, inspect `errors[*].partial_scene_changes_possible` and `scene_change_status`. A failure known to occur before execution may be corrected directly; a possible or unknown partial change requires targeted scene inspection or `hia_scene_diff` before another write. HIA does not automatically undo a failed batch. A successful Python return is not completion: verify the actual live-scene nodes or geometry and the task-relevant visual, temporal, or semantic result. Use narrower HIA tools only when they add necessary evidence; avoid a tool forest.
7. Advance the applicable Build Brief stages in semantic order: proportions and primary form, structure, mid-level assemblies, detail, materials, scoped lighting/animation/simulation/FX, then output validation. Merge or skip inapplicable stages. Use only validation evidence that settles the current claim. For simulation/cache completion, apply the reset, configured-start, range, cache, and dependency evidence rule in [build-brief-and-review.md](references/build-brief-and-review.md), and surface missing proof once as a real risk.
8. For a Full visual claim, capture only a meaningful milestone or unresolved visual question with `hia_capture_viewport`; do not capture every edit. Inspect the actual returned image content together with its objective source-state, frame-lock, capture, cook, and temporal facts as described in [visual-validation.md](references/visual-validation.md). Codex performs the visual judgment; unproven HDR/OCIO/display parity makes the screenshot diagnostic rather than final color evidence.
9. Give the preview plus relevant semantic, `hia_validate`, or `hia_scene_diff` evidence to `$houdini-artifact-review` only when independent review can change the handoff. Name the largest consequential deviation, let only the Director fix the smallest coherent region, recheck the same claim, and stop as soon as acceptance is supported.
10. If usable live capture is unavailable, mark the visual claim unverified. Report the chosen technique, material limitations, source ledger, validation evidence, and remaining gaps. Write reusable research as an original short memo under the draft-to-verified contract in [research-and-sources.md](references/research-and-sources.md); never present an unverified hypothesis as a confirmed result or promote it into the formal knowledge index.

For the active scene, default to HIA MCP V2 and HOM. Treat the main task as Director and sole writer of the current HIP; keep live `hia_*` scene I/O to a few serial calls. Use Researcher, Architect, Lookdev Reviewer, Artifact Reviewer, and Performance Reviewer only as the compact research, drafting, or read-only roles defined in [build-brief-and-review.md](references/build-brief-and-review.md). They return evidence and recommendations for the Director to apply serially. This is native Codex collaboration, not a new Agent system or backend. Never fan out parallel, repetitive node-type or help searches. If a scene write returns `HOUDINI_SESSION_CHANGED`, `HOUDINI_RUNTIME_SOURCE_CHANGED`, or `STALE_HOUDINI_RUNTIME`, stop further writes, use health or read-only inspection only as needed, then reconnect or restart normally; do not hot-reload the executor or switch routes. Use FXHoudiniMCP only as a compatibility path when the active HIA configuration explicitly selects that fallback, and describe fallback operations without binding the workflow to legacy tool names. Never switch the current scene to native `hython` automatically; use `hython` only when the user explicitly requests offline work, an independent HIP, batch processing, or background rendering. Never take over the screen.

## Guardrails

- Understand an external algorithm before translating it. Never claim arbitrary GLSL can be pasted unchanged into Karma or MaterialX.
- Prefer original authors, SideFX documentation/tutorials, original papers, and original projects. Do not copy substantial code when licensing is absent or unclear.
- Preserve the current scene and report partial changes after failures. Avoid unbounded retries; produce the diagnostic report described in visual-validation.md when its trigger is met.
- Leave Fast/serviceTier selection, conversation history, and disconnect/reconnect handling to the Panel and Bridge; do not simulate or implement them in this skill.
- Do not create another agent, planner, summarizer, chat database, knowledge or memory system, monitoring service, or network service. The user-selected local Qwen embedding encoder only supplies retrieval vectors; Codex remains the sole decision-maker.
