# Build Brief and Professional Review

Use this contract for a high-risk creation, substantial rebuild, simulation/cache task, or consequential visual delivery. Do not load the full workflow for one primitive, one known parameter or connection change, routine read-only inspection, or an ordinary API error. A Build Brief is a short design blueprint, not an intermediate representation, node list, approval gate, or promise to run every stage.

## Scale the workflow by risk

- **Direct:** execute a known deterministic edit immediately and perform one necessary targeted validation. Do not require local retrieval, a Build Brief, external research, capture, or artifact review.
- **Focused:** for a bounded multi-node edit or familiar technique, retrieve only when a node, parameter, version, project convention, or failure cause is uncertain. Use only the one or two relevant supports, such as narrow help, a compact semantic expectation, a scene diff, or one visual check.
- **Full:** use one shared batched local lookup when the task involves an uncertain or version-sensitive complex material/simulation/Solaris workflow, historical project convention, or uncertain failure cause. Add SideFX/original-source research for simulation or cache work, substantive material or color-management/render work, reference matching, unfamiliar or version-sensitive behavior, a high-cost operation, or a multi-stage deliverable. Use only the applicable compact Brief, technical evidence, and visual or professional review needed by the claim.

These are reasoning tiers, not a Gate, approval layer, state machine, or fixed tool sequence. Escalate or reduce the workflow when observed uncertainty, cost, or evidence changes. A direct color assignment remains Direct; material complexity or color-pipeline uncertainty, not the word “color” alone, raises the tier.

## Keep one compact Build Brief

For the Full tier, keep these current decisions in the Director's task context before the first scene write:

- **Goal:** intended asset, shot, effect, or behavior and the observable quality bar.
- **Reference and design language:** defining forms, motion, material, lighting, or style cues; separate evidence from assumptions.
- **Subsystems:** coherent responsibilities, dependencies, and handoffs.
- **Editable controls:** only decisions the user is likely to change.
- **Outputs:** scene roots, geometry, materials, animation, caches, USD, renders, or other requested deliverables.
- **Risks:** uncertain technique or version support, topology, scale, performance, simulation, renderer, source, or licensing concerns.
- **Stages:** only the applicable construction and review stages.
- **Acceptance:** technical and visual evidence required for each completion claim.

Record explicit required and forbidden outcomes under Goal or Acceptance. A negative constraint is hard on the observed result and its semantic role, including an equivalent substitute produced by another node or method; only the user may relax it or authorize an approximation.

Use short bullets and update only decisions that changed. Keep the Build Brief plus a compact research synthesis in the main task context. Preserve decisions, evidence, source links, risks, current stage, and unverified items; reference full documents, ledgers, and subtask artifacts by path or URL instead of pasting whole documents, long subtask replies, or source bodies.

## Turn knowledge into semantic expectations

Knowledge retrieval supplies implementation evidence; it does not prove the resulting network is correct. Before a Focused or Full write, distill only the retrieved rules that can change success into explicit semantic expectations: target path or scope, observed field/attribute/relationship, expected mapping or range, relevant frame or stage, tolerance when needed, and the evidence that would settle it.

Examples include source `flame` mapping to destination `flame`, required fields having a nonzero active range, and velocity remaining finite with magnitude plausible for the scene scale. After execution, ask the current `hia_validate` semantic-expectation capability to evaluate only these task-specific claims. Read its live tool contract at call time; do not restate MCP payload fields in the Skill or invent them from prose. An error-free cook does not satisfy a semantic expectation by itself.

If a semantic result is `unknown` or emits a `*_NOT_PROVEN` notice, expose that once as a real risk or unverified claim with the missing evidence. Do not repeat the same warning across every stage or convert absence of proof into success.

## Build in semantic stages

Advance in this order when applicable:

1. proportions and primary form;
2. structure, supports, contacts, and major negative spaces;
3. mid-level assemblies and functional components;
4. task-relevant detail;
5. materials and surface response;
6. lighting, animation, simulation, or FX that is actually in scope;
7. output and delivery validation.

Merge or skip inapplicable stages; this is not a fixed Gate or iteration count. At each visible milestone, compare the evidence with the Brief, name the largest consequential deviation, let the Director change the smallest coherent region, and recheck the same evidence. Stop when that stage's acceptance claim is supported instead of polishing indefinitely.

## Use native Codex professional roles

- **Director:** owns the compact Brief, chooses tradeoffs, and is the sole writer of the live HIP.
- **Researcher:** returns sources, provenance, technique findings, uncertainty, and a concise recommendation.
- **Architect:** returns subsystem and dependency design, network/HOM draft, controls, risks, and validation needs.
- **Lookdev Reviewer:** read-only review of material, lighting, render response, and target-image evidence.
- **Artifact Reviewer:** read-only integrated review of structure, contacts, proportions, readability, and delivery claims.
- **Performance Reviewer:** read-only review of measured cook, geometry, instancing, time dependence, cache, and delivery-cost evidence.

These are task roles within native Codex collaboration, not persistent Agents, another model, a scheduler, or a local chat system. Research and planning roles do not write the live HIP. Reviewer roles report evidence and the minimum useful correction; the Director decides and applies changes serially.

Keep every subtask return compact: **Decision**, **Evidence**, **Risks**, **Recommended next action**, and **Unverified**. Do not forward the full working transcript to the Director.

## Route professional acceptance

Select only the domains needed by the Brief:

| Domain | Judgment | Minimum useful evidence |
| --- | --- | --- |
| Modeling | Identity, proportions, hierarchy, construction, contacts, topology, and editability | Live paths and errors, geometry facts, representative view, and a relevant control/dependency check |
| Material | Material identity, bindings, primvars, texture/color handling, optical response, and displacement scale | Material summary or live paths plus a representative diagnostic or target view |
| Lighting and render | Camera intent, light direction, separation, exposure, shadows, renderer support, and delivery settings | Recorded frame/camera, light and render settings, and a representative capture or render |
| Animation | Timing, arcs, constraints, deformation, continuity, and target-frame readability | Relevant range, representative frames, live channel/constraint evidence, and observed pops or errors |
| Simulation | Scale, sourcing, collisions, stability, continuity, cache validity, and art direction | Solver/source/collision paths, reset and configured start evidence, a cook beginning at that start, representative phases or suspect interval, dependency evidence, errors, and cache/output coverage |
| Network organization | Semantic flow, names, outputs, crossings, dead experiments, and maintainable boundaries | Bounded read-only graph inspection of the affected network |
| Performance | Cook or frame cost, geometry and instance strategy, time dependence, cache behavior, and quality tradeoffs | Measured values or tool evidence from the relevant scope and an appropriate baseline; never invented estimates |

Do not turn review into a score or exhaustive checklist. Report the highest-impact issue first, its path or scope, evidence, severity, responsible role, minimum correction, and any missing proof. Read-only inspection does not trigger construction, a Build Brief, or a review-fix loop by itself.

For a simulation or cache completion claim, require evidence that the state was reset, cooking began from the configured start, the relevant range or representative phases were evaluated, the cache is current and covers the claimed output, and required upstream dependencies participated. Interpret the current `hia_validate` cook/cache evidence through its live runtime contract instead of freezing its output schema here. Any unproven item keeps the claim unverified; report the missing proof once rather than emitting a long repeated warning. Observed bounded recomputation does not by itself prove reset, range coverage, cache freshness, or dependency participation.

## Promote only a Verified Procedure

Call a workflow a **Verified Procedure** only when its relevant steps succeeded in real Houdini on a recorded build, the required technical or visual evidence supports the claim, and the user accepted the result. Only then may the Director propose it for a formal knowledge entry or reusable workflow memory; promotion is still explicit, never automatic.

A failed or merely plausible attempt is not a Verified Procedure. Keep failures in the bounded diagnostic report or unverified experience notes, and do not automatically write them to project memory. If a later corrected workflow succeeds and is accepted, promote only the bounded successful procedure with its version, scope, evidence, and limitations.
